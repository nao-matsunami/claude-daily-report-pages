A. Claude Code

A-1. auto mode が 8/14 から新規セッションの既定 permission mode に

[確認済] Pro/Max/Team 対象。自分で default mode を設定済みなら維持され、一度だけ切替プロンプトが出る。組織管理の既定は変わらない。auto mode の分類器呼び出しは既に利用上限にカウントされない。事前有効化は ~/.claude/settings.json の permissions.defaultMode: "auto"。codex・Claude 一致 + 原文確認。
→ https://code.claude.com/docs/en/whats-new/2026-w32

A-2. auto mode の根拠数値(Simon Willison 経由)

[確認済] 有料開発者 1,053人、危険コマンドを人間が拒否できたのは 13.6%、auto mode は 89% をブロック。Trajectory Labs の間接プロンプトインジェクション 72シナリオ / 720試行 で Fable 5・Opus 5・Sonnet 5 の auto mode 下は成功ゼロ。Willison 本人は「確認疲れを考えれば auto mode が優る」としつつ、悪意ある third-party パッケージ経由には懐疑的で独立検証を求めている。Claude 単独報告だが一次(本人記事)で全数値一致。
→ https://simonwillison.net/2026/Aug/8/auto-mode/

G. 3AI とも取りこぼしていた一次項目(w32 digest より)

私が原文を読んで見つけた、3つの出力のいずれにも含まれていなかった確定事項です。すべて [確認済]:

今日の注目

1. 8/14 の auto mode デフォルト化 — 今日が当日

理由: 本日発効です。既定モードを明示設定していない環境では、新規セッションの挙動が今日から変わります。意図しない変化を避けるなら ~/.claude/settings.json に permissions.defaultMode を明示するのが即効性のある対処。裏付けデータ(人間 13.6% vs auto mode 89%)は一次確認済みで説得力がありますが、Willison が指摘する「third-party パッケージ経由の攻撃」への耐性は未検証領域です。auto mode の分類器呼び出しは利用上限にカウントされないので、有効化のコスト面のデメリットはありません。

2. v2.1.229 の workflow fan-out プレフィックスキャッシュ最適化 — 実測する価値が高い

理由: サブエージェント/workflow を多用しているなら、キャッシュ取りこぼしはトークンコストに直結します。CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS=0 で無効化できるので、同一 fan-out を有効/無効で1回ずつ回して cache_read の差分を測る A/B が素直に組めます。同じ v2.1.229 の CPU制限コンテナ修正、および 200サブエージェント上限撤廃とセットで、並列運用の前提が今週まとめて変わりました。定量化された知見が現時点で存在しないので、実測する価値があります。

3. /commit-push-pr の危険フラグ非自動承認 + worktree isolation 強化 — 既存の自動化が壊れうる
