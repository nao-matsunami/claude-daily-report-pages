B. プロンプトキャッシュ公式ドキュメント（今回いちばん実務価値が高い）

B-1. How Claude Code uses prompt caching の全内容

[確認済] Claude の出力（§2）の記述は、列挙されたほぼ全項目が原文と一致。原文で確認できた要点:

  • 3層プレフィックス: System prompt（コア指示・ツール定義・output style）→ Project context（CLAUDE.md・auto memory・unscoped rules）→ Conversation。ファイル単位/セグメント単位のキャッシュは無い（"There is no per-file or per-segment caching"）。
  • モデルと effort はプロンプト本文ではないがキャッシュキーの一部。原文の Tip: "Pick your model and effort level at the top of a session, then save /compact for natural breaks between tasks."
  • キャッシュを壊す: モデル切替 / effort変更 / fast mode ON / MCPサーバ接続・切断（tool search で deferred なら壊れない、/advisor トグルも breakpoint 後なので壊れない）/ プラグイン有効無効（MCPサーバを含む場合のみ。skills・commands・agents・hooks・monitors・themes は壊さない）/ ツール名まるごとの deny ルール（Bash・WebFetch・Bash()・""。Bash(rm *) のようなスコープ付き deny と allow/ask は壊さない）/ /compact / アップグレード。
  • 壊さない: リポジトリのファイル編集 / CLAUDE.md 途中編集 / output style 変更 / 権限モード変更 / skill・コマンド呼び出し / /recap / /rewind / サブエージェント起動。
  • CLAUDE.md の途中編集は「壊さないが反映もされない」。/clear・/compact・再起動で反映。サブディレクトリのネスト CLAUDE.md と paths: frontmatter 付きルールは遅延ロードなので、ロード前の編集は効く。
  • /compact より /rewind: 原文 Tip に "If you've gone down a path you want to abandon entirely, /rewind to an earlier turn instead. Rewinding truncates back to a prefix that is already cached."
  • TTL 2バケット（設定は v2.1.242 以降）:
バケットサブスク枠内usage credits / APIキー / クラウドプロバイダ
メイン会話（対話 / -p / Agent SDK）1時間5分
それ以外（サブエージェント・workflow・teammates・fork・compaction・セッションタイトル）5分（※サーバ制御のヘルパー要求のみ1時間）5分

優先順位: FORCE_PROMPT_CACHING_5M=1 → バケットの環境変数 → バケットの設定 → ENABLE_PROMPT_CACHING_1H=1 → 既定。プラン上限を超えて usage credits に入るとメイン会話も5分に落ちる。

  • サブエージェント vs fork: サブエージェントは自前のシステムプロンプトを持つため親のキャッシュを読まない。fork は親の system prompt / tools / 履歴をそのまま継承するので初回リクエストから親のキャッシュにヒットする。workflow の fan-out では、Claude Code が最初の1体以外を一時的に保留して同一プレフィックスを共有させる。
  • スコープはマシン+ディレクトリ。システムプロンプトに作業ディレクトリ・プラットフォーム・シェル・OSバージョン・auto memory パスが埋まる。同一リポジトリの worktree 同士も共有しない。同一ディレクトリの並列セッションは共有する。逐次セッションは起動時の git status スナップショット（ブランチ・直近コミット）が一致したときのみ共有。
  • 確認方法: statusline の current_usage.cache_creation_input_tokens / cache_read_input_tokens、claude -p "hello" --output-format json の usage.cache_creation（ephemeral_1h_input_tokens / ephemeral_5m_input_tokens）。

出典: https://code.claude.com/docs/en/prompt-caching

今日の注目（検証・実装を試す価値がある更新）

1. プロンプトキャッシュ公式ドキュメントを headless 運用に落とし込む（最優先）

理由: 今回唯一、既存の自動化の実コストを直接動かせる一次情報。特に効くのが3点 —
(a) fork は親のキャッシュにヒットするが、サブエージェントはヒットしない。同一文脈の派生作業をサブエージェントで回している箇所は fork に寄せるだけで初回リクエストが安くなる。
(b) worktree はキャッシュを共有しない。「3〜5セッションを worktree 並列」（G-1）は生産性の推奨だが、キャッシュ観点では各 worktree が別プレフィックスを一から温めるというトレードオフがあり、両方の一次情報を突き合わせて初めて見える。
(c) claude -p はメイン会話バケットだが、cron が API キー / クラウドプロバイダ経由なら 5分固定。promptCacheTtl: "1h" を明示しないと1時間TTLは効かない。まず claude -p "hello" --output-format json の usage.cache_creation で ephemeral_1h_input_tokens / ephemeral_5m_input_tokens のどちらに入っているかを実測するのが、最小コストで最大の情報が得られる一手です。

2. v2.1.248 --restricted — ただし cron への適用は要注意

3. v2.1.251 PreModelSwitch / PostModelSwitch + SessionStart resume の staleness・再キャッシュコスト

理由: §B-1 の「モデル切替はキャッシュを全損させる」という知見を、初めてフックで観測・ブロックできるようになった組み合わせ。特に SessionStart resume が再キャッシュ推定コストを受け取るのは、長時間セッションの resume を続けるか /clear するかを機械的に判断する材料になる。1と2に比べれば実装コストは高いが、「キャッシュ会計をログに落とす」土台としては今週で唯一の新規手段です。
