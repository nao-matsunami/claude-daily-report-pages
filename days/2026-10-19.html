A. Claude Code 本体(最重視)

A-1. v2.1.299 アイドル時の自動圧縮(idle compaction)

[確認済](2系統一致+changelog原文)
ターミナルで20万トークンを超える会話を約54分放置すると、1時間のプロンプトキャッシュが切れる前に圧縮します。下限は CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS で変えられ、"idleCompaction": false で無効化できます(どちらも v2.1.290 以降)。v2.1.302 で /config に切り替え項目が追加されました。
出典: https://code.claude.com/docs/en/changelog

A-2. v2.1.299 CLAUDE_CODE_DISABLE_FILE_MENTIONS

[確認済](2系統一致+原文)
@ で指定したファイルは、中身ではなくパスだけが渡り、Claude がファイルツールで読みに行きます。どれだけ削減できるかの実測値は公式に示されていません。

A-3. v2.1.299 hooks の仕様変更

[確認済](Claude のみの主張、原文で確認)

  • UserPromptSubmit hook が、スキルやスラッシュコマンドの展開より前に実行されるようになりました。そのため、ブロックすれば埋め込みシェルコマンドも止まります。
  • プラグイン hook に判定を渡せない・返せないときは、許可ではなく拒否になります。
  • スキル自身の frontmatter に書いた UserPromptSubmit hook は、スキルを呼び出したプロンプトの次から動きます。

A-4. v2.1.299 その他

[確認済](Claude のみ、原文で確認)

  • 不可視文字・方向制御文字・< > を含むスキル名やコマンド名は、リネームするまで候補に出ません。
  • サブエージェントの tools: に MCP サーバー名を書くと、そのサーバーのツールだけが対象になります。サーバー名に __ を含む場合は mcp__<名前全体>__* と書く必要がある、という注記もあります。
  • /usage に新しい警告が4種類出るようになりました。
  • /reload-skills が「compaction 後にスキル一覧を再送する手段」だと明記されました。
  • Cowork のクラウドセッションでは、PermissionRequest hook でシェルやサブエージェントを承認できなくなりました。

A-5. v2.1.300 hook 入力の検証強化ほか

[確認済](Claude のみ、原文で確認)

  • PreToolUse / PermissionRequest hook が返す updatedInput を、Claude 自身の入力と同じように検証します。未知のキーは捨てられ、ツールが受け付けない入力は拒否されます。
  • Agent hook が model 設定に従うようになりました。
  • SessionEnd hook が飛ばされる問題と、--worktree で WorktreeCreate / WorktreeRemove hook が動かない問題が修正されました。
  • headless / SDK セッションを再開したときに compaction のサマリーが失われる問題が修正されました。
  • /advisor が Claude Platform on AWS で使えるようになりました。

A-6. v2.1.300 OTel でキャッシュ書き込みを5分/1時間に分けて計測

[確認済](2系統一致+原文)
api_request イベントに cache_creation_5m_tokens と cache_creation_1h_tokens が追加されました。

A-7. v2.1.301 CLAUDE_CODE_RETRY_WATCHDOG_MAX_USAGE_LIMIT_WAIT_MS

[確認済](2系統一致+原文)
無人リトライモードのとき、利用上限のリセットが遠ければ待たずにリクエストを終了します。

A-8. v2.1.301 その他

[確認済](Claude のみ、原文で確認)

  • コンテキストが小さいモデルに切り替えると、収まらない会話は切り替え前のモデルが先に要約します。
  • /rewind の後にスキル一覧がモデルに渡らない問題が修正されました。
  • 引数名の埋め込みは先頭64個(各64文字まで)に制限されました。
  • Vim の % モーションと、claude-api スキルへの OTel ガイドが追加されました。

A-9. v2.1.302 fork サブエージェントの既定有効化と、サードパーティでの権限モード初期値

[確認済](2系統一致+原文)

  • fork サブエージェントが claude -p、Agent SDK、Desktop、VS Code でも既定で有効になりました。無効化は CLAUDE_CODE_FORK_SUBAGENT=0 です。
  • サードパーティのプロバイダーでは、権限モードを指定しない -p / SDK セッションが default で始まります(テレメトリ無効時、または新規インストール時)。
  • Desktop と VS Code では、メイン会話のサブエージェントが常にバックグラウンドで動きます。

A-10. v2.1.302 その他

[確認済](原文で確認)

  • prompt / agent hook は、同じイベントで同時に最大12個まで実行されます。
  • CLAUDE_CODE_AUTO_MODE_MODEL が追加されました。クライアント側の auto mode 分類器のモデルを選ぶもので、サーバー側の auto mode は変わりません。
  • Claude in Chrome の指示文の位置が変わり、共有プロンプトキャッシュを再利用できるようになりました。
  • 途中で追加したツールの ToolSearch や compaction 後のキャッシュミスが修正されました。
  • compaction 中に停止したときの「Prompt is too long」が修正されました。

A-11. Code Review の一般提供開始(10/15)

[確認済](2系統一致+公式ブログ)

  • 対象は Team / Enterprise です。リポジトリごとに Quick / Standard(既定)/ Deep を選べます。
  • 所要時間は約20分から6〜10分に短縮されました(約3倍)。これは提供元が示した数字です。
  • 条件を満たす Enterprise 組織は、2027/1/15 までに最低 $10,000 分のクレジットを申請できます(申請から30日で失効)。この点は Claude のみの主張ですが、原文で確認しました。

出典: https://claude.com/blog/code-review-is-now-generally-available

A-12. 公式チーム記事「How the Claude Code team does code review」(10/15)

[確認済](codex のみ、claude.dev で原文確認)

  • CLAUDE.md は短くし、領域ごとに REVIEW.md を置きます(失敗の具体例、対象外パス、細かな指摘の上限、file:line での根拠)。
  • 完了宣言の前に、テストやビルドを実行させて結果を示させます。
  • 新しいコンテキストのサブエージェントでレビューします。
  • レビューと修正の往復は3ラウンドで方針を見直し、以降は差分だけを再レビューします。
  • 記事内の成果は、1ラウンドで通る割合が 65%→78%、レビュー回数の平均が 2.08→1.32 です。

出典: https://claude.dev/blog/solving-code-review-at-anthropic/

今日の注目

  1. hooks の安全側への変更(v2.1.299 / 2.1.300 / 2.1.302)
  • 内容: UserPromptSubmit がスキル展開より先に動くようになり、プラグイン hook は判定不能なら拒否になり、updatedInput が厳しく検証され、prompt / agent hook は同時12個までになりました。
  • 理由: 入力を書き換える hook や、多数の prompt hook を使っている自動化では、黙って拒否されたり待たされたりする可能性があります。既存の hook 棚卸し(pretooluse-auto-allow-inventory.md、hook-if-condition-misfire-impact.md)に、この観点を足して再監査する価値があります。
  1. OTel の cache_creation_5m_tokens / cache_creation_1h_tokens と、アイドル圧縮・CLAUDE_CODE_DISABLE_FILE_MENTIONS
  • 理由: 1時間キャッシュの前提が実際の運用で効いているかを、初めて直接計測できるようになりました。idle-compaction-cache-premise-doc-check.md の前提を実測で確かめられます。
  1. 公式チームのレビュー運用(REVIEW.md、3ラウンド上限、差分のみの再レビュー)
  • 理由: この「収集→審判→検証」パイプライン自体にそのまま使えます。具体的には、検証ループの収束条件と、file:line 形式の根拠を必須にすることです。数値付きの一次情報なので、取り込んだ後に効果を比べやすいです。
